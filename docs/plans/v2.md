# v2 — the rest of the Improvement Brief (P1 + P2)

## Summary
P0 shipped in PR #7. This plan covers the remaining brief: new roles (Manager, Technician,
Accountant), approvals and an audit log, a full product master with suppliers and weighted-average
cost, installation jobs, two-step transfers, reservations, stock counts, printable documents, a
role-aware dashboard, ten new reports and the settings and warehouse fields. WooCommerce is built
last, behind a feature flag. Everything stays on Hostinger (app + MariaDB). Scheduled jobs run as
Hostinger **cron jobs** that call a secret-protected route in the app.

The ledger rules do not change: entries are append-only, StockLevel changes only inside the entry
transaction, a void is a reversing entry. Every new flow below is built **out of ordinary ledger
entries** plus side tables, so the existing stock-card, void and integrity logic keeps working.

## Non-goals
- Barcode scanning (the `barcode` field is added, unique when set, nothing reads it yet).
- Purchase orders / accounting (cost is recorded for valuation only; no invoices, payables or VAT returns).
- Moving any data or service off Hostinger.

## Design principles (how the brief fits the v1 rules)
1. **Approvals never touch the ledger until approved.** A correction/write-off/void over the
   threshold is saved as an `ApprovalRequest` (the full entry payload as JSON + who asked). Approving
   calls `createEntry` / `voidEntry` with the requester recorded; rejecting stores the reason. So
   "entry does not affect stock until approved" holds and no entry is ever edited.
2. **Custody and transit are warehouses.** New system warehouse kinds `IN_TRANSIT` (one) and
   `TECHNICIAN` (one per technician, created with the user). Issue to technician = transfer into his
   custody warehouse; dispatch = transfer into In transit; receive = transfer out of In transit.
   On-hand, stock card, void and integrity check all work unchanged; reports group these kinds
   separately so they never count as sellable.
3. **Cost is append-only too.** Unit cost lives on `StockEntryLine.unitCost`. "Cost pending" lines
   (Staff left it blank) get a `CostRecord` row later from a Manager/Admin; average cost is computed
   from lines + cost records, never by editing a line. Price/cost edits on the product are audit-logged.
4. **Reservations are not stock movements.** `Reservation` + lines; Available = On hand − Reserved
   (sellable warehouses). Dispatch turns it into a normal OUT entry in the same transaction and
   releases it; the stock-out check uses Available for other users' sales.
5. **One-line rule for new uniqueness** (website order no., supplier invoice): generated column
   (`NULL` when voided) + unique index, as already done for voids (H5).

## Phases
Each phase is its own `feature/v2-<phase>` branch and PR, merged to `main` (so Hostinger deploys it)
only after `pnpm verify`, the auditor and a browser run in EN + AR. Detailed tasks/tests per phase are
written into this file when the phase starts.

### Phase A — Roles, approvals, audit log, security
- Roles Manager / Technician / Accountant with the brief's rights; the permission table in CLAUDE.md
  updated. Accountant: read-only + cost. Technician: only "My jobs" (Phase C adds the screen).
- Cost visibility: Admin + Accountant (+ Manager for entering delivery costs). **Supersedes Q11.**
- Approval rules in Settings (corrections, damaged/lost, voids: above X units or Y SAR). Pending list
  on the dashboard; approve / reject with reason. Void becomes Admin or the warehouse's Manager.
- Audit log page (Admin): product price/cost, roles, warehouse settings, approvals, before/after.
- Security: min password length 10, forced change on first login and after an admin reset, idle
  session timeout (setting, default 8 h), login rate limit stored in MariaDB (works across Hostinger
  restarts/processes), login history per user, last login on Users, last-admin guard kept.
- Email password reset **only if SMTP is configured** (Hostinger mailbox: `SMTP_HOST/PORT/USER/PASS`);
  otherwise the link is hidden and admins reset as today.

#### Phase A — detailed (branch `feature/v2-a`)
**Roles and rights** (`src/lib/permissions.ts`, `src/lib/stock/policy.ts`)
| Role | Rights |
|------|--------|
| ADMIN | everything; never needs approval |
| MANAGER | stock in/out/transfer, corrections, damaged/lost, return to supplier, void — **assigned warehouses only**; approves requests for those warehouses; no products/warehouses/users/settings, no cost |
| STAFF | as v1, plus **requests** corrections and damaged/lost in assigned warehouses |
| TECHNICIAN | only "My jobs" (empty until Phase C) and his own account page |
| ACCOUNTANT | read-only everywhere + cost + audit log |
| VIEWER | read-only (unchanged) |
New actions: `approval:decide` (ADMIN, MANAGER), `audit:view` (ADMIN, ACCOUNTANT), `settings:manage` (ADMIN), `openingStock:import` (ADMIN — opening stock no longer rides on `entry:correct`), `job:own` (TECHNICIAN).

**Approvals** (`src/server/stock/approvals.ts`)
- Rules in Settings, one per kind — corrections, damaged/lost, voids: "save directly up to **N units** and **S SAR**"; default N = 0 → every non-admin one needs approval. Value = Σ qty × product cost; lines without a cost count by units only.
- `createEntryInTx` / `voidEntryInTx` check the rule after their validation and throw `ApprovalRequiredError` before taking a number (defence in depth). `submitEntry` / `submitVoid` catch it in the same transaction and save an `ApprovalRequest` (`REQ-000001`, payload, units, value, warehouse(s), the form's idempotency key) instead.
- Approver: ADMIN, or a MANAGER assigned to every warehouse the request touches; **never the requester**. Approve = lock the request `FOR UPDATE`, run the entry/void with the requester as creator (rights re-checked then), mark APPROVED + link the entry, audit. If stock is short at approval time, nothing changes and the request stays pending. Reject needs a note. The requester can cancel while pending. One pending void request per entry (generated column + unique index).
- Screens: `/approvals` (pending / mine / decided), `/approvals/[id]` (lines, units, value for cost roles, approve / reject / cancel); wizard and void dialog show "Sent for approval — REQ-…"; entry page shows "Approved by …"; dashboard card "Pending approvals".

**Audit log** (`AuditLog`, `src/server/audit.ts`, `/admin/audit`)
- Written in the same transaction as the change; only changed fields, before → after: product create/update (incl. cost), product import (one summary row), user create/update/activate/password reset (never the hash), warehouse create/update/activate, settings, approval decisions. Filters: area, user, dates; 50 per page.

**Security**
- New passwords ≥ 10 characters (sign-in still accepts older shorter ones). `mustChangePassword` on new users and after an admin reset (and on the first admin) → every page/action redirects to `/account/password` until changed. Everyone can change their own password there.
- Sessions: 8 h idle (sliding), 24 h absolute; a password change/reset signs that user out everywhere (`passwordChangedAt` vs the session's sign-in time).
- Sign-in limits stored in MariaDB (`LoginEvent`): 5 failed tries per email or 30 per IP in 15 min → "Too many attempts, try again in 15 minutes". Every attempt is logged (email, IP, result); `lastLoginAt` on success. Users list shows last login; `/admin/users/[id]` shows login history.
- Email password reset → Phase G (needs SMTP, together with the weekly email).

**Migration** `20261014…_roles_approvals_audit`: `Role` enum += MANAGER, TECHNICIAN, ACCOUNTANT; `User` += `mustChangePassword`, `passwordChangedAt`, `lastLoginAt`; `LoginEvent`, `AuditLog`, `ApprovalRequest` (+ `pendingVoidOf` guard), `Setting`; counter `REQ`.

**Tests**: permissions/policy matrix (unit); approvals (thresholds, admin bypass, own-request block, manager scope, approve → entry, short stock keeps pending, reject, cancel, duplicate pending void, idempotent submit); audit rows for each action; login limits/history/forced change/session invalidation; Technician and Accountant page access.

**Done when:** `pnpm verify` green; browser run in EN + AR: staff correction → pending → manager approves → stock changes; manager void → admin approves; forced password change on first login; lockout after 5 bad passwords; audit log shows a product cost change; technician sees only My jobs; accountant sees cost but no Stock in/out.

#### Phase B — detailed (branch `feature/v2-b`, stacked on `feature/v2-a`)
**Product master** (`Product`, product form, `/admin/products`)
- New fields: SKU (unique; blank = model code; existing products get their model code), barcode (unique when set,
  digits/letters only), WooCommerce SKU (next to the existing WooCommerce ID), selling price (SAR incl. VAT, visible to
  everyone), status (Active / Discontinued / Inactive — replaces `active`), size range, colour, max load (kg), VESA,
  default supplier, lead time (days). "Variant" stays as "Other details". All attributes are searchable.
- Status rules: Active = everything. Discontinued = today's "inactive" (can't be received, can still leave, be
  transferred or corrected; not reordered). Inactive = retired: only when it holds no stock anywhere; no movements
  (voids still work); hidden from pickers and stock reports.
- Image upload: resized in the browser (800 px + 240 px thumbnail, JPEG), stored in MariaDB (`ProductImage`, Q3),
  served by `/api/product-images/[id]` to signed-in users. `imageUrl` holds that path (an external https URL still works).
- Cost history (cost roles): every change of the product cost is kept (`ProductCost`); the weighted average from
  delivery costs comes with per-line delivery costs in Phase C.
- Reorder level + reorder quantity per warehouse (`ProductReorder`); the product's low-stock level stays the default.
  Low stock = a warehouse with its own level at or below it, or (no own levels) total sellable ≤ default; only Active.
- Products list: thumbnail, model code / SKU, name, category, on hand per warehouse, total sellable, total damaged,
  stock value (cost roles), status; Excel export of the same rows.
- Import: new columns (sku, barcode, woosku, wooproductid, sellingprice, sizerange, colour, maxloadkg, vesa,
  leadtimedays, supplier); duplicate SKU/barcode checks (file + database); "Download rows with errors" (.xlsx with an
  error column). Import still never changes status.

**Suppliers** (`Supplier`, `/admin/suppliers`)
- Name EN/AR, contact person, phone, email, city, country, VAT no., payment terms, notes, active. ADMIN and MANAGER
  manage them (`supplier:manage`); anyone who records a delivery can add one inline (name + phone).
- Supplier delivery and return to supplier: searchable supplier picker ("Add new supplier") instead of free text.
  The entry keeps `supplierId` + the name at that moment. Duplicate invoice: the review step warns when the same
  supplier + invoice no. already has a non-voided delivery (saving is still possible).

**Migration** `…_product_master_suppliers`: Product fields + `status` (from `active`), `ProductImage`, `ProductCost`,
`ProductReorder`, `Supplier`, `StockEntry.supplierId`; existing free-text supplier names are left on old entries.

**Tests**: status rules in createEntry; SKU/barcode uniqueness; import (new columns, duplicates, error file);
reorder-level low stock; supplier CRUD + inline add permissions; duplicate-invoice check; cost history; image upload
limits + access; products list / export never send cost to non-cost roles.

**Done when:** `pnpm verify` green; browser (EN + AR, phone + desktop): create a product with image, attributes,

### Phase C — Stock in / out improvements
- Supplier delivery: unit cost per line, "Cost pending" badge + filter, PO/reference, multiple photos.
- Customer return: original order no. or link to the original OUT entry, return reason, cannot
  return more than was sold on that order (minus earlier returns).
- Website order: order no. required, format check, **unique among non-voided website orders**.
- Direct sale: Saudi phone check (already normalised), receipt no., payment method, salesperson.
- **Installation jobs:** Issue (job no., technician, date, customer, phone, district/address) →
  stock moves to his custody warehouse → Close job per line: installed (OUT · Installation from
  custody), returned unused (transfer back), damaged (transfer to a Damaged warehouse or write-off).
  Open jobs list with age; Technician's mobile "My jobs" screen.
- **Two-step transfers:** Dispatch (source → In transit) → Receive at destination (enter received
  qty). Short/over → discrepancy for Manager decision (write off as lost, return to source, or accept).
  Old one-step transfers stay valid history. Transfer into a Damaged warehouse is labelled "Move to
  damaged" with a required reason.
- Return to supplier: supplier, RMA no., reason, expected credit, status Sent → Credit received
  (status change is a side-table update, the ledger entry is untouched).
- Damaged/lost: reason category, photo required for "Broken", approval above threshold; the UI
  explains *Move to damaged* (transfer, still ours) vs *Write off* (gone) — matches Q3.
- Corrections ±: reason required, approval rules from Phase A.
- Product picker: available qty in the chosen warehouse; quantity input capped at it.

#### Phase C is shipped in two parts
- **C1 — entry details and costs** (branch `feature/v2-c1`): delivery costs + weighted average, customer returns
  against the original sale, website/direct-sale/return-to-supplier/damaged fields, several photos.
- **C2 — jobs and transfers** (branch `feature/v2-c2`): installation jobs with technician custody, two-step

#### Phase C1 — detailed
**Delivery costs** (`LineCost`, one per delivery line; lines themselves stay immutable)
- Supplier delivery: unit cost per line, entered by ADMIN / MANAGER (`cost:enter`). Staff leave it empty; the entry
  is then **Cost pending** (badge, filter on Entries, count for cost roles). A manager/admin fills it on the entry
  page later; a wrong cost can be corrected there (audit-logged).
- **Weighted-average cost** per product = Σ(qty × unit cost) ÷ Σ qty over non-voided supplier-delivery lines with a
  cost (`averageCosts()`); used for stock value wherever a cost is shown, falling back to the product's own cost
  when no delivery has a cost yet. Every delivery cost is also added to the product's cost history (DELIVERY).
- Managers see the costs they enter on that entry only; product cost and stock value stay ADMIN / ACCOUNTANT.

**Customer return** — "Order no. or entry no." is required (an `OUT-…` number links the original entry,
`originalEntryId`); a return reason (wrong size, changed mind, defective, damaged in delivery, installation
cancelled, other). Units returned (all non-voided returns on that order) can't exceed the units sold on it; the
order must match a recorded sale (older sales: use Correction +, decision PC1).

**Stock out** — Website order: order no. normalised (`#12345` → `12345`, digits only) and a review warning when a
non-voided website order with that number exists (an order can ship from two warehouses, so not a block, PC2).
Direct sale: payment method (cash / card / transfer, required), receipt no., salesperson (defaults to the user).
Return to supplier: RMA / reference, reason, expected credit (SAR), status Sent → Credit received (+ amount and
date; a side table, the entry is untouched). Damaged / lost: reason category (broken in warehouse, broken in
delivery, missing, expired/obsolete); a photo is required for "broken"; approval rules unchanged.

**Photos** — up to 5 per entry (stock in, damaged / lost) via `EntryAttachment`; `photoUrl` keeps the first.

**Migration** `…_entry_details_costs`: `StockEntry` += `reasonCode`, `paymentMethod`, `salesperson`,
`originalEntryId` (FK, ON UPDATE RESTRICT); `LineCost`, `EntryAttachment`, `SupplierReturn`.

**Tests**: cost pending + fill later + WAC; returns over the sold quantity (by entry no. and by order no.), voided
returns don't count; website order normalising + warning; direct sale fields; supplier return status; damaged photo
rule; approvals carry the new fields; cost never reaches non-cost roles (managers only on their entry form/page).

### Phase D — Reservations
- Create from the Stock-out screen (website/phone order, confirmed but not dispatched); On hand /
  Reserved / Available everywhere stock is shown; dispatch → OUT entry; cancel; expiry setting.

### Phase E — Stock counts
- Create (warehouse, full or by category) → blind sheet on mobile → submit → Manager variance report
  (units + SAR) → approve → linked Correction ± entries posted automatically.
- Method: **snapshot at count start**, and movements during the count are added to the expected
  quantity, so the shop does not have to stop selling (no locking).
- Shrinkage report (month / warehouse / category).

### Phase F — Documents, dashboard, reports
- Numbering per Q1. Bilingual print views: Goods received note, Delivery note, Transfer note, Gate
  pass, with logo, signature lines, Riyadh date. Success screen: number, Print, View, Record another.
- Dashboard KPIs from the brief, role-aware, warehouse filter.
- Reports 1–10 from the brief with filters in the URL, Excel + PDF (see Q2), EN/AR headers.

### Phase G — Settings, warehouses, UX, operations
- Settings page (company name/logo EN/AR, VAT %, thresholds, low-stock defaults, numbering prefixes,
  default warehouse per user). Warehouse fields; deactivation blocked while holding stock with a
  "Transfer all stock" shortcut.
- Autosave draft per user (in the database, so it follows the user to another device), remember last
  warehouse, first-run checklist, numeric keypad/steppers, RTL and accessibility pass.
- Nightly integrity check (cron → `/api/cron/integrity`, recompute StockLevel from the ledger, flag
  differences on the dashboard, never auto-fix); weekly low-stock + pending-approvals email (if SMTP);
  Admin export (Excel workbook of all tables) next to Hostinger's own daily backups.
- Demo seed: ~40 products in 4 categories, 3 warehouses, 3 months of movements (`pnpm db:seed:demo`,
  refuses to run on a database that already has entries).

### Phase H — WooCommerce (feature flag `WOO_ENABLED`, off by default)
- Push available qty of sellable warehouses after each movement (in-app outbox table processed
  after the transaction and by the cron route — no external queue); match by `wooProductId` / `wooSku`.
- Webhook (HMAC-verified) → Reservation for new orders. Sync log page with Retry.
- Needs WooCommerce REST keys from hamoodtv.com when switched on.
