# v2 — the rest of the Improvement Brief (P1 + P2)

## Summary
P0 shipped in PR #7. This plan covers the remaining brief: new roles (Manager, Technician,
Accountant), approvals and an audit log, a full product master with suppliers and weighted-average
cost, installation jobs, two-step transfers, reservations, stock counts, printable documents, a
role-aware dashboard, ten new reports and the settings and warehouse fields. WooCommerce is built
last, behind a feature flag. Everything stays on Hostinger (app + MariaDB). Scheduled jobs run as
Hostinger **cron jobs** that call a secret-protected route in the app.

The ledger rules do not change: entries are append-only, StockLevel changes only inside the entry
transaction, a void is a reversing entry. Every new flow below is built **out of ordinary ledger
entries** plus side tables, so the existing stock-card, void and integrity logic keeps working.

## Non-goals
- Barcode scanning (the `barcode` field is added, unique when set, nothing reads it yet).
- Purchase orders / accounting (cost is recorded for valuation only; no invoices, payables or VAT returns).
- Moving any data or service off Hostinger.

## Design principles (how the brief fits the v1 rules)
1. **Approvals never touch the ledger until approved.** A correction/write-off/void over the
   threshold is saved as an `ApprovalRequest` (the full entry payload as JSON + who asked). Approving
   calls `createEntry` / `voidEntry` with the requester recorded; rejecting stores the reason. So
   "entry does not affect stock until approved" holds and no entry is ever edited.
2. **Custody and transit are warehouses.** New system warehouse kinds `IN_TRANSIT` (one) and
   `TECHNICIAN` (one per technician, created with the user). Issue to technician = transfer into his
   custody warehouse; dispatch = transfer into In transit; receive = transfer out of In transit.
   On-hand, stock card, void and integrity check all work unchanged; reports group these kinds
   separately so they never count as sellable.
3. **Cost is append-only too.** Unit cost lives on `StockEntryLine.unitCost`. "Cost pending" lines
   (Staff left it blank) get a `CostRecord` row later from a Manager/Admin; average cost is computed
   from lines + cost records, never by editing a line. Price/cost edits on the product are audit-logged.
4. **Reservations are not stock movements.** `Reservation` + lines; Available = On hand − Reserved
   (sellable warehouses). Dispatch turns it into a normal OUT entry in the same transaction and
   releases it; the stock-out check uses Available for other users' sales.
5. **One-line rule for new uniqueness** (website order no., supplier invoice): generated column
   (`NULL` when voided) + unique index, as already done for voids (H5).

## Phases
Each phase is its own `feature/v2-<phase>` branch and PR, merged to `main` (so Hostinger deploys it)
only after `pnpm verify`, the auditor and a browser run in EN + AR. Detailed tasks/tests per phase are
written into this file when the phase starts.

### Phase A — Roles, approvals, audit log, security
- Roles Manager / Technician / Accountant with the brief's rights; the permission table in CLAUDE.md
  updated. Accountant: read-only + cost. Technician: only "My jobs" (Phase C adds the screen).
- Cost visibility: Admin + Accountant (+ Manager for entering delivery costs). **Supersedes Q11.**
- Approval rules in Settings (corrections, damaged/lost, voids: above X units or Y SAR). Pending list
  on the dashboard; approve / reject with reason. Void becomes Admin or the warehouse's Manager.
- Audit log page (Admin): product price/cost, roles, warehouse settings, approvals, before/after.
- Security: min password length 10, forced change on first login and after an admin reset, idle
  session timeout (setting, default 8 h), login rate limit stored in MariaDB (works across Hostinger
  restarts/processes), login history per user, last login on Users, last-admin guard kept.
- Email password reset **only if SMTP is configured** (Hostinger mailbox: `SMTP_HOST/PORT/USER/PASS`);
  otherwise the link is hidden and admins reset as today.

### Phase B — Product master + suppliers
- Product fields above; list with thumbnail, on-hand per warehouse, sellable/damaged totals, value
  (cost roles), Excel export. Import gets row-level preview + "download error rows".
- Suppliers page (EN/AR names, contact, VAT no., terms, active); searchable supplier picker with
  "Add new" inline; duplicate invoice warning (same supplier + invoice no., non-voided).
- Weighted-average cost from supplier deliveries (moving average, recalculated from the ledger, so a
  void of a delivery is reflected). Cost history screen per product.
- Images: uploaded, resized **in the browser** to 800 px + 200 px thumbnail (no native image library —
  the Hostinger build machine can't load native binaries, H13), stored like delivery photos (see Q3).

### Phase C — Stock in / out improvements
- Supplier delivery: unit cost per line, "Cost pending" badge + filter, PO/reference, multiple photos.
- Customer return: original order no. or link to the original OUT entry, return reason, cannot
  return more than was sold on that order (minus earlier returns).
- Website order: order no. required, format check, **unique among non-voided website orders**.
- Direct sale: Saudi phone check (already normalised), receipt no., payment method, salesperson.
- **Installation jobs:** Issue (job no., technician, date, customer, phone, district/address) →
  stock moves to his custody warehouse → Close job per line: installed (OUT · Installation from
  custody), returned unused (transfer back), damaged (transfer to a Damaged warehouse or write-off).
  Open jobs list with age; Technician's mobile "My jobs" screen.
- **Two-step transfers:** Dispatch (source → In transit) → Receive at destination (enter received
  qty). Short/over → discrepancy for Manager decision (write off as lost, return to source, or accept).
  Old one-step transfers stay valid history. Transfer into a Damaged warehouse is labelled "Move to
  damaged" with a required reason.
- Return to supplier: supplier, RMA no., reason, expected credit, status Sent → Credit received
  (status change is a side-table update, the ledger entry is untouched).
- Damaged/lost: reason category, photo required for "Broken", approval above threshold; the UI
  explains *Move to damaged* (transfer, still ours) vs *Write off* (gone) — matches Q3.
- Corrections ±: reason required, approval rules from Phase A.
- Product picker: available qty in the chosen warehouse; quantity input capped at it.

### Phase D — Reservations
- Create from the Stock-out screen (website/phone order, confirmed but not dispatched); On hand /
  Reserved / Available everywhere stock is shown; dispatch → OUT entry; cancel; expiry setting.

### Phase E — Stock counts
- Create (warehouse, full or by category) → blind sheet on mobile → submit → Manager variance report
  (units + SAR) → approve → linked Correction ± entries posted automatically.
- Method: **snapshot at count start**, and movements during the count are added to the expected
  quantity, so the shop does not have to stop selling (no locking).
- Shrinkage report (month / warehouse / category).

### Phase F — Documents, dashboard, reports
- Numbering per Q1. Bilingual print views: Goods received note, Delivery note, Transfer note, Gate
  pass, with logo, signature lines, Riyadh date. Success screen: number, Print, View, Record another.
- Dashboard KPIs from the brief, role-aware, warehouse filter.
- Reports 1–10 from the brief with filters in the URL, Excel + PDF (see Q2), EN/AR headers.

### Phase G — Settings, warehouses, UX, operations
- Settings page (company name/logo EN/AR, VAT %, thresholds, low-stock defaults, numbering prefixes,
  default warehouse per user). Warehouse fields; deactivation blocked while holding stock with a
  "Transfer all stock" shortcut.
- Autosave draft per user (in the database, so it follows the user to another device), remember last
  warehouse, first-run checklist, numeric keypad/steppers, RTL and accessibility pass.
- Nightly integrity check (cron → `/api/cron/integrity`, recompute StockLevel from the ledger, flag
  differences on the dashboard, never auto-fix); weekly low-stock + pending-approvals email (if SMTP);
  Admin export (Excel workbook of all tables) next to Hostinger's own daily backups.
- Demo seed: ~40 products in 4 categories, 3 warehouses, 3 months of movements (`pnpm db:seed:demo`,
  refuses to run on a database that already has entries).

### Phase H — WooCommerce (feature flag `WOO_ENABLED`, off by default)
- Push available qty of sellable warehouses after each movement (in-app outbox table processed
  after the transaction and by the cron route — no external queue); match by `wooProductId` / `wooSku`.
- Webhook (HMAC-verified) → Reservation for new orders. Sync log page with Retry.
- Needs WooCommerce REST keys from hamoodtv.com when switched on.

## Risks
| Risk | Mitigation |
|------|------------|
| Arabic in server-generated PDFs (letter shaping, RTL) is unreliable in JS PDF libraries | Q2 |
| Hostinger redeploys replace the app folder; files written there can be lost | Q3 (store in DB) |
| Multiple Node processes on Hostinger → in-memory rate limits/caches diverge | rate limits and drafts in MariaDB |
| Cron availability | Hostinger Business includes cron jobs; every scheduled task can also be run by hand from Settings |
| Database size from images | thumbnails ≤ 60 KB, originals ≤ 300 KB after browser resize |
| Scope (~8 phases) | phases ship independently; each is usable on its own |
